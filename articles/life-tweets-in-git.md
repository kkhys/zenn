自分の人生を、自分の手元に書き残しておきたい。そんな自分専用のマイクロブログが、ずっと欲しいと思っていました。

X や Instagram のような中央集権型 SNS に言葉を積み上げ続けるのは、どうにも気が乗りません。理由を突き詰めると、全データが運営会社に握られているという一点に行き着きます。買収や破綻で消えるかもしれないし、何かの拍子に凍結されれば書き溜めたものは一瞬で読めなくなる。ライフログを預ける先としては、あまりに心許ない。

そこで一度は、分散型 SNS の Mastodon を自前で建てました。VPS に Arch Linux を入れ、ActivityPub を喋るおひとり様インスタンスを立ち上げたわけです。

https://kkhys.me/blog/posts/b1ffkqq

これはこれで楽しかったのですが、運用してみて分かったのは、自分が本当に欲しかったのはサーバではなかったということでした。

おひとり様とはいえ Mastodon は立派な Web サービスです。PostgreSQL、Redis、Sidekiq、Nginx、Ruby と動かすべきものは多く、稼働すれば終わりのない運用が始まります。OS のアップグレード、本体のバージョン追従、証明書の更新、DB のバックアップ。そして、攻撃も絶え間なく続きます。fail2ban のログを覗いたら、稼働 1 週間で SSH 接続の失敗が 8,110 回、811 個の IP アドレスをブロックしていました。誰も見ていない個人のつぶやき置き場ですら、世界中から休みなくアクセスを試みられます。

ここで我に返りました。僕がやりたかったのは、自分の言葉を、自分の手元に、流れていかない形で残すことです。フェデレーションも、フォロー機能も、いいねをもらう体験も、正直なところ要らなかった。要らない機能のために 24 時間動くサーバを守り続けるのは、どう考えても割に合いません。

ならばサーバそのものを捨ててしまえばいい。そう考えて作り直したのが、つぶやきをすべて Markdown として Git で管理する静的サイトです。

https://memo.kkhys.me

https://github.com/kkhys/memo

ここからは、その設計と実装を棚卸ししていきます。

## AI 時代にあえてつぶやきを選んだ理由

![memo のタイムライン画面。写真付きのつぶやきが時系列に並んでいる様子](/images/life-tweets-in-git/01.png)

先に、技術より動機の話を少しだけ。

生成 AI が日常になってから、情報の流れが目に見えて速くなりました。半年前のベストプラクティスがもう古い、ということが珍しくありません。こういう時代に大事なのは情報の鮮度だと感じています。重厚なブログ記事を一本書き上げる頃には、その内容の旬が過ぎていることすらある。

かといって、気づきや短いメモを X に流すと、それはタイムラインに流れて、二度と見つけられません。しかも、その言葉の所有権は自分の手元には残らない。

僕が欲しかったのは、その中間にあるレイヤーでした。

- ブログ記事ほど重くない、思いついたらすぐ書ける軽さ
- X のように流れて消えず、自分の資産として積み上がる永続性
- そして、データを完全に自分で所有していること

この `memo` はその軽量アウトプット基盤として作りました。ブログに書くほどではない発見を、鮮度が高いうちに、自分の形式で書き留めておく場所です。

しかも書く内容は技術の話に限りません。読んだ本のメモ、飲んだお酒の記録、その日のランニングのログ。ブログにするほどではない断片なら何でも、同じタイムラインに時系列で放り込んでいます。技術メモも日々のログも分け隔てなく積もっていくので、あとから眺めると、それがそのまま自分の人生の記録 ―― ライフログになっています。

## ブログを作るのは簡単になったが、書き続けるのは難しい

もうひとつ、最近強く感じていることがあります。

AI のおかげで、自作ブログを立ち上げるハードルは劇的に下がりました。デザインも、フレームワークの選定も、デプロイの設定も、AI に任せれば一日で形になります。僕自身、このサイトの大半も AI と一緒に書きました。

でも、本当に大変なのは作ることではありません。記事を書き続けることです。一本のブログ記事には、構成を練り、論理を通し、推敲を重ねるという、それなりの気合いが要ります。立派な箱を作ったのに、中身が数本で止まってしまう。そういう個人サイトを、僕は数えきれないほど見てきましたし、自分でも何度かやりました。

だから、もしこれから個人サイトを作るなら、いきなりブログから始めなくてもいいと思っています。まずは、つぶやきサイトです。一行から書ける。完成度を気にしなくていい。それでも自分の資産として積み上がっていく。書くことのハードルを限界まで下げておけば、アウトプットは自然と続きます。とくにエンジニアなら、その仕組みを毎日使っている道具の上に作ってしまえば、新しく覚えることは何もありません。そうして溜まった断片が、いつかブログ記事の種になることもあります。

作る側のハードルを AI が下げてくれた今こそ、書く側のハードルも下げる仕組みが必要だ。そう考えると、つぶやきサイトは AI 時代の最初の一歩として、けっこう理にかなっていると思います。

## サーバを一切持たない構成にした

設計の出発点は、サーバを一切持たないことでした。

- つぶやき（最大 500 文字）は、Markdown としてプライベートな Git リポジトリに置く
- それを Astro で完全な静的サイトにビルドする
- Cloudflare Pages で配信する

技術スタックは次のとおりです。

| 用途           | 採用したもの                    |
|--------------|---------------------------|
| フレームワーク      | Astro            |
| 言語           | TypeScript     |
| スタイル         | CSS |
| Lint / Format | Biome                     |
| テスト          | Vitest                    |
| ホスティング       | Cloudflare Pages          |

データベースはありません。管理画面もありません。ランタイムで動くサーバもありません。あるのは、Markdown ファイルと、それを静的 HTML に変換するビルドだけです。

## Markdown にしたのは AI と相性がいいから

つぶやきの保存形式に Markdown を選んだのには、はっきりした理由があります。AI との相性が圧倒的にいいからです。

プレーンテキストとしての Markdown は、いまや LLM にとっての共通語です。読むのも、書くのも、編集するのも、構造を理解するのも得意な形式です。独自のデータベースに閉じ込めた瞬間、その中身を AI に渡すには変換が必要になりますが、Markdown なら最初から、人間にも AI にも等しく読めます。

しかも Git 管理されているので、全文がただのテキストファイルとしてローカルに存在します。

- `grep` で全つぶやきを横断検索できる
- 差分が履歴として残る
- 別のツールへの移行が、ディレクトリをコピーするだけで済む
- そして、AI エージェントが直接読み書きできる

実際、後述するように Claude Code から直接つぶやきを投稿できるようにしています。データの永続性と AI フレンドリーさを同時に満たす形式として、Markdown + Git は最もシンプルで素直な解のひとつだと思っています。

## コンテンツの実体は、プライベートリポジトリの submodule

一番こだわったのは、アプリケーションのコードとつぶやきの中身を別リポジトリに分ける構成です。コンテンツは Git submodule として切り出しています。

```text
memo/                  # アプリ本体（パブリックリポジトリ / OSS）
├── src/
└── memo-content/      # コンテンツ（プライベートリポジトリのsubmodule）
    └── memo/
        └── 20251001_204021/   # 1投稿 = 1ディレクトリ
            ├── index.md
            ├── 01.jpg
            └── 02.jpg
```

ポイントは、コンテンツ側のリポジトリはプライベートだということです。アプリのコードは OSS として堂々と公開する一方で、つぶやきの生データや下書き、編集履歴は自分だけのものとして閉じておきたい。

`index.md` には `isDraft` というフラグがあり、本番ビルドでは下書きが除外されます。つまり、公開サイトに出るのは完成したつぶやきだけで、書きかけの思考や非公開のメモはプライベートリポジトリの中に留まります。公開と非公開の境界を、リポジトリの可視性という最も単純な仕組みで引いているわけです。

このおかげで、データの所有は Mastodon より徹底しています。僕の投稿は DB ダンプでも独自フォーマットでもなく、`git clone` すれば読める Markdown の束です。Cloudflare や GitHub が明日消えても、手元のクローンさえあれば全文がそのまま残ります。

開発時に submodule がなくても動くよう、フィクスチャデータへ切り替えるフラグも用意しています。CI や手元の開発では本物のコンテンツを必要とせず、本番ビルドのときだけプライベートな submodule を引いてきます。

```ts
const basePath =
  process.env.USE_FIXTURE_DATA === "true"
    ? "./src/__fixtures__/memo-sample"
    : "./memo-content/memo";
```

## つぶやきは CLI と Claude Code から投稿する

![Zed のエディタとターミナルで、つぶやきを書いてコミットするまでの投稿フローのデモ](/images/life-tweets-in-git/02.gif)

投稿の体験は、できる限り摩擦を減らしました。狙ったのは、つぶやくために専用のアプリを開いたり、わざわざ頭を切り替えたりしなくて済むことです。

エンジニアにとって、エディタとターミナルと git は、一日のほとんどを過ごす場所です。コードを書く手の延長でコミットを打ち、ブランチを切る。その操作はもう考えなくても指が動くくらい染みついています。だったら、つぶやきもその同じ場所で完結させてしまえばいい。新しい SNS アプリの使い方を覚える必要も、書くたびにブラウザへ持ち替える必要もありません。すでに手に馴染んだ道具の上に乗せるだけで、投稿のコストは限りなくゼロに近づきます。

コンテンツ側のリポジトリには、2 つのスクリプトを置いています。

```json
{
  "scripts": {
    "memo": "bun run scripts/create-memo.ts",
    "sy":   "bun run scripts/sync.ts"
  }
}
```

`bun run memo` を叩くと、投稿時刻を聞かれます（Enter で現在時刻）。入力された時刻をシードに ULID（時刻順にソートできる識別子）を生成し、`memo/YYYYMMDD_HHMMSS/index.md` を作り、フロントマターを埋めて、そのままエディタで開いてくれます。

```ts
const id = ulid(timestamp).toLowerCase();        // 指定時刻をシードに生成（後半はランダム）
const dirName = dateTimeToDirectoryName(createdAt); // 20251001_204021
createMemo(dirName, id, createdAt);
execFileSync("zed", [indexPath]);                 // エディタで開く
```

書き終えたら `bun run sy` を叩くだけ。変更をすべてステージし、タイムスタンプ付きのメッセージでコミットし、プッシュします。

```ts
const status = await $`git status --porcelain`.text();
if (!status.trim()) process.exit(0);
await $`git add -A`;
await $`git commit -m ${"feat: update memos " + timestamp}`;
await $`git push`;
```

つまり、思いつく → `memo` → 書く → `sy`。これだけでつぶやきが投稿できます。

さらに、僕はこの投稿フローを Claude Code のスラッシュコマンドにもしています。ターミナルで Claude Code に一行渡すだけで、ULID 生成からファイル作成までを代わりにやってくれます。

```text
/memo Astroで開発する際はAstro Docs MCPを使うのがおすすめ。
```

手を止めずに、対話の流れのまま思いつきを投げ込める。作業中にふと得た知見を、コンテキストを切らさずそのまま投稿できるのは、想像以上に快適でした。Markdown + Git という素朴な土台だからこそ、AI エージェントに投稿を任せるのが自然にできるわけです。

![Claude Code をターミナルで操作し、スラッシュコマンドからつぶやきを投稿している画面](/images/life-tweets-in-git/03.png)

## つぶやきはプレーンテキストとして扱う

つぶやきは Markdown ファイルに書いていますが、僕はそれを Markdown として整形してほしくありませんでした。`# あ` と書いて見出しになったり、`- りんご` が箇条書きになったりするのは、つぶやきの体験として明らかにおかしい。つぶやきは整形された文書ではなく、ツイートのような素のテキストであってほしい。

そこで、remark のパーサーをラップして、Markdown 記法をパースの前にバックスラッシュでエスケープするプラグインを書きました。ツリーを後から書き換えるのではなく、構文として解釈される前にプレーンテキストへ落としたかったので、パース処理自体に手を入れる形にしています。見出し、リスト、引用、インラインコード、コードブロック、水平線などが対象です。

実際のコードは記法ごとに処理を分けていますが、おおまかには次のような形です。

```ts
const remarkEscapeSyntax: Plugin<[], Root> = function (this: Processor) {
  const originalParse = this.parser?.prototype?.parse ?? this.parser;

  this.parser = (doc: string) => {
    let text = doc;
    text = text.replace(/^(#{1,6})\s/gm, "\\$1 ");   // 見出し # を \# に
    text = text.replace(/^(\s*)>\s/gm, "$1\\> ");    // 引用 > を \> に
    text = text.replace(/^(\s*)([*\-+])\s/gm, "$1\\$2 "); // リスト記号を退避
    return originalParse.call(this, text);
  };
};
```

ただし、太字（`**`）・斜体（`*`）・打ち消し（`~~`）だけは、remark がバックスラッシュを多重に解釈する都合でうまくエスケープできず、ここは既知の制限として残っています。とはいえ、つぶやきで太字を打ちたくなる場面はほとんどないので、実用上は困っていません。

裏を返せば、リンクだけはあえてエスケープしていません。URL を貼ればリンクとして機能してほしいからです。何を素のままにし、何を機能させるか。この線引きが、つぶやきの体験を決めていると思います。

## 500 文字制限を、ビルドで物理的に守らせる

短文投稿サービスを名乗る以上、文字数制限は守りたい。ですが、そのためにランタイムやフォームを用意するのは静的サイトの思想に反します。

そこで文字数チェックも、remark プラグインとしてビルドパイプラインに差し込みました。本文が 500 文字を超えていたら例外を投げるだけです。

```ts
const remarkWordLimit = () => (tree: Root) => {
  const totalLength = mdastToString(tree).length;
  if (totalLength > 500) {
    throw new Error(
      `Character count exceeds the limit: ${totalLength} characters`,
    );
  }
};
```

`throw` した瞬間にビルドが止まります。つまり 500 文字を超えたつぶやきは、そもそもデプロイされ得ない。制約をビルドに肩代わりさせて、壊れたものを世に出さないこと。これが静的サイトの強みです。

## スレッドも引用も、ULID の参照だけで成立する

![memo のスレッド表示画面。1 つのつぶやきにぶら下がる返信が縦に連なっている様子](/images/life-tweets-in-git/04.png)

返信のスレッド表示と引用は SNS らしい体験として欲しい機能でした。これもサーバを持たず、フロントマターの参照だけで実現しています。

返信したい投稿の ULID を `comment` に書けば、それは返信として扱われます。ビルド時に全投稿を舐めて、親 ULID をキーにした Map を組み立てれば、ツリー構造が再構築できます。

```ts
const buildCommentMap = (memos: Memo[]): Map<string, Memo[]> => {
  const commentMap = new Map<string, Memo[]>();
  for (const memo of memos) {
    if (memo.data.comment) {
      const existing = commentMap.get(memo.data.comment) ?? [];
      commentMap.set(memo.data.comment, [...existing, memo]);
    }
  }
  return commentMap;
};
```

引用も同じ発想で、引用先の ULID を辿って埋め込みカードを描画するだけです。リレーションを外部キーではなく、Markdown に書かれた ID 参照で表現していると言ってもいい。ビルド時に全投稿を走査するので投稿数に対して線形のコストはかかりますが、個人のつぶやきの規模で問題になることはありません。データベースがなくても、関連は十分に表現できます。

## ブログと OSS を bot として自分だけのタイムラインに集める

![memo の Blog Feed bot のプロフィールページ。ブログの新着記事が bot 投稿として並んでいる様子](/images/life-tweets-in-git/05.png)

ここが、この仕組みで一番気に入っている部分です。

つぶやきの読み込みには Astro のカスタムローダーを自作しています。このローダーはローカルの Markdown を読むだけでなく、ビルド時に 2 つの外部ソースを取り込みます。

ひとつは、自分のブログの RSS フィードです。`kkhys.me/rss.xml` を取得し、新着記事を `isBot: true` の bot 投稿として生成します。もうひとつは、自分の OSS プロジェクトの一覧。こちらも同様に bot 投稿として流し込みます。

```ts
const id = generateRssEntryId(item.guid);
const body = `${item.title}\n\n${item.link}`;
const data = await parseData({
  id,
  data: { id, createdAt: new Date(item.pubDate), author: "blog-feed", isBot: true }, // isDraft など一部は省略
});
const digest = generateDigest(data);
if (store.get(id)?.digest === digest) continue;  // 変化がなければスキップ
store.set({ id, data, body, rendered: await renderMarkdown(body), digest });
```

digest を比較して、変化のないエントリはスキップする差分更新になっています。

これによって、`memo` は単なるつぶやき置き場ではなく、自分の活動が集まってくる、専用のタイムラインになりました。ブログを書けば自動で流れてくる。OSS を公開すれば自動で流れてくる。将来的には、GitHub の草や Zenn の記事、読んだ本の記録なども、同じように bot として合流させられます。

中央集権型 SNS では、タイムラインに何が流れるかをアルゴリズムが決めていました。ここでは、それを自分のコードで完全に定義しています。何を流すかの主導権が、運営会社ではなく自分の手にある。これはサーバを捨ててもなお手放したくなかった感覚でした。

## 静的サイトなのに無限スクロールする

![memo のタイムラインをスクロールすると、次ページのつぶやきが継ぎ足されて無限に表示される様子](/images/life-tweets-in-git/06.gif)

つぶやきが増えてくると、タイムラインは無限スクロールにしたくなります。しかし静的サイトには追加データを返す API がありません。

ここで使ったのが、ページネーションされた静的 HTML そのものをデータソースにする方法です。2 ページ目以降の HTML はビルド時にすでに生成されているので、IntersectionObserver が末尾を検知したら次ページの HTML を fetch し、DOMParser でパースして、コンテナの中身を今の DOM に継ぎ足します。コンテナの子要素はすべて投稿カードなので、そのまま append するだけで済みます。

```ts
const response = await fetch(url);              // 次ページの静的HTMLを取得
const html = await response.text();
const doc = new DOMParser().parseFromString(html, "text/html");
const nextContainer = doc.getElementById(containerId);

for (const card of Array.from(nextContainer.children)) {
  container.appendChild(card);                  // 子要素はすべて投稿カード
}
```

専用の API も JSON も要りません。すでにある静的ページを、そのままデータとして再利用しているだけです。実際にはローディング表示やエラー処理、`rootMargin` による先読みも加えていますが、考え方の中心はこれだけです。

## あえて SSR を使わず完全な SSG にした

Astro は SSR もできますが、このサイトはあえて完全な静的生成にしています。

理由はシンプルで、SSR を選んだ瞬間に結局サーバが必要になるからです。リクエストごとに動くプロセスがあるということは、監視すべき対象が増え、攻撃対象が増え、運用が戻ってくるということです。それは Mastodon から逃げてきた当のものでした。

つぶやきの性質を考えても、SSG が理にかなっています。

- コンテンツが変わるのは、投稿したときとビルドしたときだけ
- リクエストごとに動的に変える必要のあるものが何もない
- 一度焼いた HTML は、CDN に置いて無限にキャッシュできる
- 自分で運用・監視するサーバがないので、守るべき攻撃対象がぐっと減る

SSR は便利な道具ですが、それは状態がリクエストごとに変わるからこそ価値があります。ほとんど静止しているコンテンツに動的サーバをあてがうのは、僕にとっては過剰でした。あの SSH 攻撃の山を見たあとでは、自分で守るべきサーバがないことの安心感は何物にも代えがたいものがあります。もちろん Cloudflare や GitHub のアカウントといった守るべき対象は残りますが、24 時間自分で面倒を見るプロセスがなくなっただけでも、運用とセキュリティの負担はまるで違いました。

## なぜ Cloudflare Pages なのか

ホスティングに Cloudflare Pages を選んだ理由も、SSG の方針と地続きです。

- 個人サイトの規模なら無料で運用できる
- 世界中のエッジに配信される高速な CDN
- GitHub と連携し、main にマージされたら自動でビルド & デプロイ
- サーバの面倒を一切見なくていい

静的な HTML とアセットをグローバル CDN に置く、という SSG の理想に対して、Cloudflare Pages はまさにぴったりの置き場でした。Mastodon 時代に毎月払っていた VPS 代も、ここではゼロになりました。

## CI でコンテンツを同期する仕組み

![GitHub 上で自動生成された submodule 更新の PR。CI が作成し auto-merge された様子](/images/life-tweets-in-git/07.png)

最後に、運用フローです。Mastodon を捨てた最大の理由は運用負荷だったので、ここは徹底的に自動化しました。

仕組みはこうです。

1. コンテンツ側のプライベートリポジトリに `bun run sy` でつぶやきをプッシュする
2. 毎日深夜 2 時、アプリ本体の GitHub Actions が cron で起動する
3. submodule の参照を最新に更新し、差分があれば PR を自動作成して auto-merge する
4. main が進むと、Cloudflare Pages が自動でビルド & デプロイする

ワークフローの中核はこのあたりです。

```yaml
on:
  schedule:
    - cron: "0 17 * * *"  # 02:00 JST
  workflow_dispatch:
```

```bash
# submoduleを最新に追従させ、差分を検出する
cd memo-content
git fetch origin main
git reset --hard origin/main

# 差分があれば、submodule参照を更新するPRを作って自動マージ
gh pr create --base main --head "$BRANCH" \
  --title "[main] chore: update submodule" --assignee kkhys
gh pr merge --auto --squash --delete-branch
```

死活監視も、OS のアップグレードも、証明書の更新も、攻撃への対処も、もうありません。アプリ側の依存ライブラリの更新も Renovate に任せ、CI が通れば自動マージ。僕がやることは、つぶやきを書いて `sy` を叩くことだけになりました。

## 一般的な SNS との使い分け

念のため補足すると、僕は X を完全にやめたわけではありません。向き不向きで使い分けています。

X のような中央集権型 SNS が得意なのは、リーチと会話と発見です。たくさんの人に届けたいとき、誰かと議論したいとき、リアルタイムの話題を拾いたいとき。ここはネットワーク効果が効く場所で、自前の静的サイトでは作れない価値があります。

一方で `memo` が担うのは、所有とアーカイブと鮮度です。誰かに見せるための言葉ではなく、自分のために残す言葉です。バズを狙わずに、ただ思考の断片を時系列に積んでいく場所です。

副次的な効果として、時間が溶けないというのも大きい。`memo` のタイムラインに並ぶのは、自分の投稿と、自分が選んだ bot だけです。他人の投稿が無限に流れてくることはありません。X のフィードは、つい眺め続けてしまうように設計されていますが、`memo` には消費するものが何もない。開いて、書いて、閉じる。ただそれだけの場所です。読むためではなく、書くために開くサイトになりました。

X は流すための場所、`memo` は残すための場所。そう割り切ると、両方ともずっと気楽に使えるようになりました。

## これからは AI とタイムラインを育てていきたい

この仕組みの面白いところは、つぶやきがすべて構造化された Markdown のコーパスとして手元に残ることです。これは AI にとって扱いやすい素材になります。

いくつか、これから試したいことを書いておきます。

- 全つぶやきを AI に渡し、自分の関心や思考の変遷を要約させる
- セマンティック検索で、過去の自分の断片を意味から引き当てる
- 散らばったつぶやきから、AI にブログ記事の下書きを起こしてもらう
- 自分の発信を要約する AI を、新たな bot アカウントとしてタイムラインに加える

つぶやきを軽く投げ込み、それを AI が束ね、編集し、より大きなアウトプットへ育てていく。人間が grep できる土台は、そのまま AI がコンテキストとして読める土台でもあります。ブログ記事が重厚な完成品だとすれば、この `memo` は AI と一緒に育てていく、思考の断片の集まりになり得ます。

中央集権型 SNS に預けた言葉では、こんなことはできません。データを自分の形式で所有しているからこそ、AI を自分の側の道具として呼び込める。これが、いま Markdown + Git でつぶやきを持つことの、最大の意味だと考えています。

## さいごに

Mastodon を建てたとき、僕は自分のサーバを持つことがデータの所有だと思っていました。

でも運用してみて気づいたのは、サーバを持つというのは所有というより管理だということです。24 時間動き続ける何かの面倒を見続ける限り、それは資産であると同時に負債でもあります。

本当に欲しかったのは、サーバではありませんでした。流れていかない言葉と、いつでも手元に取り出せるデータ。それだけなら、Markdown のテキストファイルと Git のコミット履歴で十分すぎるほど足りていました。

面白いのは、見た目は SNS そのものだということです。タイムラインは無限にスクロールし、つぶやきにはスレッドがぶら下がり、ブログや OSS が bot として流れてくる。けれど、その実体は流れていきません。Source of Truth は、自分のリポジトリに刻まれたコミット履歴だからです。流れていく UI と、流れていかない実体。これが、僕の作りたかったものです。

情報の流れが速い AI 時代だからこそ、軽く速くアウトプットしたい。でも、その言葉は自分の手元に、自分の形式で残しておきたい。そして願わくば、その蓄積を AI と一緒に育てていきたい。

つぶやきは、流れていかなくていい。自分の人生は、誰かのサーバではなく、自分のリポジトリに残しておく。これからも、一行ずつ書き溜めていきます。
